# 搜索性能

粗筛的开销几乎都在地形逐列生成上. 实测 (6400 x 1800 中世界, `cols` 3400, 96 列观测):

| 阶段 | 占比 |
| --- | --- |
| 逐列地形生成 | 91% 到 98% |
| 观测评分 | 2% 到 9% |

所以优化集中在每列随机数的消耗次数和单次消耗的成本上, 评分侧不值得改动.

## 随机数改为整数

`UnifiedRandom.Next(max)` 的原语义是 `(int)(Sample() * max)`, 其中 `Sample()` 的乘数是
`1/2147483647` 的双精度表示. 于是它等于 `sample * max / 2147483647` 向下取整.

原实现每取一个随机数都要做整型转双精度, 两次双精度乘法, 再转回整型. 消费级显卡的双精度
吞吐只有单精度的 1/64 (Ada 架构), 因此这一步在 CUDA 上代价极高.

改为整数后, 只需一次 64 位乘法加一次除以常数 (编译期会展开成乘法移位):

```cpp
(int)((unsigned long long)sample * (unsigned)max / 2147483647ull)
```

等价性依据: 双精度两次舍入造成的绝对误差不超过 `2^-52 * max`. 当 `max` 不超过 2^20 时,
该误差小于 2.4e-10, 而任何非整数结果到整数的距离至少是 `1/2147483647` 约 4.66e-10, 且
2147483647 是质数, 不会整除 `sample * max`, 所以整数式与双精度式逐位相同.

`max` 超过 2^20 时仍走原来的双精度式. 这不是保守: 实测 `max = 2147483647` 时双精度会少 1,
该调用只出现在被重置前的初始化段且结果被丢弃, 保留双精度式可以完全避免分歧.

验证方式是对生成逻辑实际用到的 20 个区间, 遍历全部 2^31 个随机数值逐一比对, 结果零处不符.
WebGPU 内核本来就受限于没有 64 位整数, 一直用两个 32 位字模拟乘除, 因此不受影响, 无需改动.

## 生成到窗口末尾即止

地形只在观测窗口 `[w0, w1)` 内被读取. 原实现每次都推进到 `cols`, 窗口右侧的列算完即丢.
现在循环到 `min(w1, cols)` 就停止. 输出与随机数消费顺序在窗口内完全不变, 只是不再继续
推进永远用不到的部分.

## 其它清理

- `rock` 只参与自身比较, 从不影响输出, 但它内部的 `while` 循环会消耗随机数. 保留随机数
  消耗, 去掉累加与钳制.
- 坡度增量始终是整数, 改为 `int` 累加后一次性并入双精度地表高度.
- CPU 后端默认线程数上限从 8 放宽到 64, 以用满逻辑核心.

## 实测

同机 100 万种子, Windows 侧 RTX 4060 Laptop, 观测与参数完全相同:

| 实现 | 耗时 | 相对 |
| --- | --- | --- |
| CUDA 改前 | 3.93 s | 1.00x |
| CUDA 改后 | 1.09 s | 3.6x |

CPU 后端墙钟计时, 20 万种子, 8 线程 (4 物理核):

| 实现 | 耗时 | 速度 | 相对 |
| --- | --- | --- | --- |
| 改前 | 3.577 s | 55910 种子/秒 | 1.00x |
| 改后 | 2.570 s | 77835 种子/秒 | 1.39x |

单线程基准 (同一进程内分别计生成与评分):

| 实现 | 生成 | 完整流程 |
| --- | --- | --- |
| 改前 | 11471 种子/秒 | 10837 种子/秒 |
| 改后 | 19668 种子/秒 | 17410 种子/秒 |

单线程约 1.6 倍, 但 8 线程时超线程共享执行资源, 提升收敛到 1.39 倍. 说明单核效率改善
不会线性放大到多线程吞吐.

CUDA 上评分只占约 3%: 把偏移组合从 41 个减到 1 个, 100 万种子只从 1.09 s 降到 1.06 s,
因此生成是唯一瓶颈.

## 等价性验证

- 20 万种子 x 41 个组合: 改前改后的 `matched` 计数同为 15075, 候选文件逐字节相同.
- CUDA 100 万种子: 候选文件哈希相同 (500 行).
- 随机数: 20 个实际区间在全部 2^31 个随机数上逐一比对, 零处不符.
- 仓库测试全绿, 含原生与浏览器参考实现的对拍.

## 尝试过但未采用

把每线程 228 B 的共享内存随机数状态改为线程本地数组以提升占用率, 实测反而慢 1.58 倍
(1.06 s 变成 1.67 s): 线程本地数组的随机下标访问会退化成不合并的全局访问, 共享内存才是
正确的存放位置.

## 仍然存在的上限

扫描 2^31 个种子时, 每个种子要先把世界从第 0 列推进到出生点附近, 即约 3000 列, 而窗口只有
一百多列, 96% 的逐列模拟是为了把随机数状态推进到位. 减法式随机数虽然是模 2^31-1 上的线性
递推, 可以写成矩阵幂, 但每列消耗的随机数次数取决于分支结果, 无法确定要跳多少步, 因此没有
可行的跳步办法. 这部分开销与算法无关, 只能靠降低单列成本来压缩.
