# 搜索性能

粗筛的开销几乎都在地形逐列生成上. 实测 (6400 x 1800 中世界, `cols` 3400, 96 列观测):

| 阶段 | 占比 |
| --- | --- |
| 逐列地形生成 | 91% 到 98% |
| 观测评分 | 2% 到 9% |

所以优化集中在每列随机数的消耗次数和单次消耗的成本上, 评分侧不值得改动.

## 随机数改为整数

`UnifiedRandom.Next(max)` 的原语义是 `(int)(Sample() * max)`, 其中 `Sample()` 的乘数是
`1/2147483647` 的双精度表示. 于是它等于 `sample * max / 2147483647` 向下取整.

原实现每取一个随机数都要做整型转双精度, 两次双精度乘法, 再转回整型. 消费级显卡的双精度
吞吐只有单精度的 1/64 (Ada 架构), 因此这一步在 CUDA 上代价极高.

改为整数后, 只需一次 64 位乘法加一次除以常数 (编译期会展开成乘法移位):

```cpp
(int)((unsigned long long)sample * (unsigned)max / 2147483647ull)
```

等价性依据: 双精度两次舍入造成的绝对误差不超过 `2^-52 * max`. 当 `max` 不超过 2^20 时,
该误差小于 2.4e-10, 而任何非整数结果到整数的距离至少是 `1/2147483647` 约 4.66e-10, 且
2147483647 是质数, 不会整除 `sample * max`, 所以整数式与双精度式逐位相同.

`max` 超过 2^20 时仍走原来的双精度式. 这不是保守: 实测 `max = 2147483647` 时双精度会少 1,
该调用只出现在被重置前的初始化段且结果被丢弃, 保留双精度式可以完全避免分歧.

验证方式是对生成逻辑实际用到的 20 个区间, 遍历全部 2^31 个随机数值逐一比对, 结果零处不符.
WebGPU 内核本来就受限于没有 64 位整数, 一直用两个 32 位字模拟乘除, 因此不受影响, 无需改动.

## 生成到窗口末尾即止

地形只在观测窗口 `[w0, w1)` 内被读取. 原实现每次都推进到 `cols`, 窗口右侧的列算完即丢.
现在循环到 `min(w1, cols)` 就停止. 输出与随机数消费顺序在窗口内完全不变, 只是不再继续
推进永远用不到的部分.

## 其它清理

- `rock` 只参与自身比较, 从不影响输出, 但它内部的 `while` 循环会消耗随机数. 保留随机数
  消耗, 去掉累加与钳制.
- 坡度增量始终是整数, 改为 `int` 累加后一次性并入双精度地表高度.
- CPU 后端默认线程数上限从 8 放宽到 64, 以用满逻辑核心.

## 实测

同机 100 万种子, Windows 侧 RTX 4060 Laptop, 观测与参数完全相同:

| 实现 | 耗时 | 相对 |
| --- | --- | --- |
| CUDA 改前 | 3.93 s | 1.00x |
| CUDA 改后 | 1.09 s | 3.6x |

CPU 后端墙钟计时, 20 万种子, 8 线程 (4 性能核 + 4 能效核):

| 实现 | 耗时 | 速度 | 相对 |
| --- | --- | --- | --- |
| 改前 | 3.577 s | 55910 种子/秒 | 1.00x |
| 改后 | 2.570 s | 77835 种子/秒 | 1.39x |

单线程基准 (同一进程内分别计生成与评分):

| 实现 | 生成 | 完整流程 |
| --- | --- | --- |
| 改前 | 11471 种子/秒 | 10837 种子/秒 |
| 改后 | 19668 种子/秒 | 17410 种子/秒 |

线程缩放 (改后实现, 20 万种子): 1 线程 17093, 2 线程 32777, 4 线程 60466, 8 线程 86425 种子/秒.
1 到 4 线程接近线性 (3.54 倍), 再多的四个线程落在能效核上, 所以 8 线程的整体倍数收敛到 1.39 倍.

单列约 57 周期, 而每列大约有 66 条指令, 折算 IPC 只有 1.2 左右. 远低于现代乱序核心的能力,
说明单线程不是吞吐受限, 而是被随机数状态带来的串行依赖和分支预测失败拖住. 这正是下一步
可以回收的空间.

CUDA 上评分只占约 3%: 把偏移组合从 41 个减到 1 个, 100 万种子只从 1.09 s 降到 1.06 s,
因此生成是唯一瓶颈.

## 等价性验证

- 20 万种子 x 41 个组合: 改前改后的 `matched` 计数同为 15075, 候选文件逐字节相同.
- CUDA 100 万种子: 候选文件哈希相同 (500 行).
- 随机数: 20 个实际区间在全部 2^31 个随机数上逐一比对, 零处不符.
- 仓库测试全绿, 含原生与浏览器参考实现的对拍.

## Apple GPU (MLX)

MLX 后端把同一套逐列生成和评分写成 Metal 源码, 由 MLX 在运行时编译并调度, 主机侧只负责
分批和候选维护. 它存在的意义不是换一种算法, 而是让 macOS 上的主机进程也能直接用 GPU:
浏览器 WebGPU 后端虽然同样跑在 Metal 上, 但必须保持页面打开.

M1 (8 核, 4 性能 + 4 能效) 实测, 同样的观测和参数:

| 实现 | 种子/秒 | 相对 |
| --- | --- | --- |
| 8 线程 CPU | 77835 | 1.00x |
| MLX, 随机数状态放线程私有数组 | 127203 | 1.63x |
| MLX, 随机数状态放 threadgroup 内存 | 227504 | 2.92x |

状态存放位置是这里最关键的取舍. 每线程 56 个整数的环形缓冲如果放在线程私有数组里, 随机
下标访问会落到本地内存, 吞吐直接掉到 56%. 放进 threadgroup 内存后恢复正常.
线程组大小 32 / 64 / 128 分别是 212796 / 223367 / 228034 种子/秒, 再往上受 32 KB
threadgroup 内存限制. 端到端 (含 3% 到 9% 的评分) 200 万种子耗时 10.19 s, 约 197089 种子/秒.

另外两点和 CUDA 不同:

- 苹果 GPU 的 64 位整数除法很慢, 用 `ulong` 直接算 `sample * max / 2147483647` 实测只有
  152289 种子/秒, 必须沿用 WebGPU 内核里那两个 32 位字的乘除模拟.
- MLX 每次启动都要从源码编译一次 Metal 内核, 约 1.2 s. 所以主机侧的工作块设成 400 万种子,
  否则固定开销会吃掉收益.

结果与 CPU 逐位一致: 同一种子的 6400 列剖面完全相同, 20 万种子的 `matched` 计数同为 4064,
候选文件逐字节相同.

## 再压一轮: 随机数的控制依赖链

上一轮把每列的乘法除法换成整数后, 剩下的大头是"样本 → 分支 → 下一个样本"这条控制依赖链.
按 55 循环可以推出下一步要读的两个槽位号, 它只依赖计数, 与取值无关, 因此可以在算当前样本的
同时把下一步要读的两个字读进寄存器.

RTX 4060 Laptop, 100 万种子, 3400 列, 41 个偏移. 所有变体的候选文件哈希相同, 耗时取多次
交错运行的最好值 (笔记本 GPU 有 3% 左右的温度漂移):

| 变体 | 耗时 | 说明 |
| --- | --- | --- |
| 原实现 | 1.03 s 到 1.05 s | 双精度地表, 乘法除法判零 |
| 全整数地表 + 阈值比较 | 0.95 s | 去掉每列约 7 次双精度运算 |
| 再加样本预取 | 0.87 s | 去掉共享内存延迟造成的等待 |
| 再把 `surface_offset` 改成无分支 | 0.69 s | 提交的版本, 相对最初约 1.5 倍 |
| 只跑剖面内核 | 0.76 s | 评分内核占 0.08 s (9%) |
| 只跑随机数 (每列 4 次) | 0.32 s | 无分支, 无地形 |
| 只跑地形算术 (无随机数) | 0.28 s | 无随机数 |

## 分枝发散才是最大的浪费

坡度增量函数原来是按特征 0 到 4 的 5 路 `switch`. 特征由逐 lane 的随机数决定, 一个 warp 里
几乎每种特征都会出现, 硬件只能把各条路径串行执行一遍, 等于每列多跑三四遍函数体.

1 到 4 号特征其实是同一个结构: 两个"随机数判零就加减一"的循环, 只是阈值和方向不同.
把阈值从 `(2^31 - 2) / k` 展开成常量, 方向用一次 select 选出, 就能用同一份代码跑完四种特征,
不留分支. 只有特征 0 的循环体要多抽一个增量, 单独保留一条分支.

| 变体 | 中位数耗时 |
| --- | --- |
| 保留 5 路 switch | 0.875 s |
| 改成无分支参数选择 | 0.692 s |

五轮交错测量, 候选文件哈希不变, 20 万种子逐列剖面哈希零差异. 相对最初的双精度版本,
累计 1.05 s 到 0.69 s, 约 1.5 倍.

把特征 0 也并进同一个循环体的写法试过但不对: 第二步循环即使不进循环体也要先判一次,
而判零本身会消耗一个样本, 特征 0 原来的路径根本不进第二步, 样本数就对不上了.

三个和直觉相反的结论:

- **bank 填充没有收益.** 每线程 56 个整数时, 32 个 lane 只落在 4 个 bank 上, 理论上 8 路冲突;
  改成 57 (与 32 互素) 后仍然一样快. 原因是分支发散让同一指令里各 lane 的槽位号并不一致,
  冲突假设不成立.
- **占用率不是瓶颈.** 占 384 线程/SM (每线程 228 B 共享内存, 3 块 x 128 线程, 100 KB/SM),
  改成 64 线程块把上限抬到 448 线程后没有变化, 说明不是并发链数不够.
- **主机端没有明显变化.** 8 线程 CPU 三次交错测量在 2.30 s 到 2.56 s 之间波动, 与改动前的
  区间重叠, 所以预取与否对主机路径没有可分辨的差别.

阈值比较的依据是 `Next(k) == 0` 等价于 `sample <= (2^31 - 2) / k`. 这里的 k 全是编译期常量,
阈值被折叠成一条整数比较, 省掉一次 32x32 乘法与 2^31-1 的常数除法.

地表改用 1/8 格整数的依据是: 首列必定被钳到 306, 之后增量都是整数, 所以整数累加与双精度累加
逐位相同. 注意 `6400 * 0.55` 的双精度结果是 `3520.0000000000005`, 原条件 `x < 3520` 实际包含
x = 3520, 整数化时必须写成 `x <= 3520`, 否则会漏掉一列的特征重抽.

## 为什么没有跳过式的算法加速

粗筛里 96% 的逐列模拟是为了把随机数状态从第 0 列推进到出生点附近, 看起来应该能跳过去.
减法式随机数是模 2^31-1 上的线性递推, 状态推进确实可以写成矩阵幂: 跳 m 步只需要一次
55 x 55 的矩阵向量乘. 但前进的步数由取值决定: 每列消耗几次随机数取决于 `Next(k) == 0`
这类分支的结果, 而要知道这些结果就得把样本算出来. 想跳过计算, 就得先知道跳多少步;
想知道跳多少步, 就得先算完. 这不构成循环, 而是一条真正的串行依赖, 所以没有可以跳过的区间.

同样行不通的还有: 把随机数状态放到寄存器 (按数据相关的下标访问必须落到内存), 把状态拆到
warp 各 lane 上 (那样一个 warp 只能算一个种子, 失去 32 路并行), 以及用位切片一次算 32 个
种子 (模 2^31-1 的进位修正和多尺度缩放比直接算更贵).

剩下的空间在指令数上: 每列还有 4 个与取值无关的分支 (海滩区间, 两个特征重抽区间), 可以按
列区间把循环切成几段分别展开, 预计再省 10% 左右; 评分内核一个 block 只用 41 个线程 (256 个
线程里 215 个空闲), 改成每个 warp 处理一个种子还能再要回几个百分点.

## 尝试过但未采用

把每线程 228 B 的共享内存随机数状态改为线程本地数组以提升占用率, 实测反而慢 1.58 倍
(1.06 s 变成 1.67 s): 线程本地数组的随机下标访问会退化成不合并的全局访问, 共享内存才是
正确的存放位置.

## 仍然存在的上限

扫描 2^31 个种子时, 每个种子要先把世界从第 0 列推进到出生点附近, 即约 3000 列, 而窗口只有
一百多列, 96% 的逐列模拟是为了把随机数状态推进到位. 减法式随机数虽然是模 2^31-1 上的线性
递推, 可以写成矩阵幂, 但每列消耗的随机数次数取决于分支结果, 无法确定要跳多少步, 因此没有
可行的跳步办法. 这部分开销与算法无关, 只能靠降低单列成本来压缩.
