# 过程复盘

按时间顺序记录走过的路, 包括那些后来被证明是死路的分支. 保留它们的价值在于:
每一步失败都给出了"什么不是原因", 而最后定位到真因靠的正是这些排除.

## 阶段 0: 拿到算法

目标版本是 1.4.5.8. 用 dnSpy 对 `Terraria.exe` 做类型导出, 得到 `Terraria.WorldGen`.
关键认识是每个 pass 进入时都会重新播种, 所以只要按顺序复现 pass 内的随机数消耗, 地表高度就能算出来.

## 阶段 1: 移植并用存档对拍

移植了初始化段与地形 pass 到 C 和 Python.

对拍对象是用户自己建的 `dev1` 存档 (中型 / 专家 / 猩红 / 种子 123456) —— 注意这三个参数
**与最终要找的目标世界完全相同**, 所以这次对拍同时也验证了"邪恶类型不影响随机数消耗顺序"
这个假设.

对拍结果: WorldId, treeX, treeStyle, caveBackX, caveBackStyle, 冰/地狱/丛林背景样式,
8 个背景样式, moonType, 地牢方位, leftBeachEnd —— 全部一致. 移植本身是可信的.

## 阶段 2: 地图路线 (死路)

最初用的是地图截图, 提取出 658 列地表剖面. 灌了 CPU 版, Windows 机器, WSL 三处并行扫描.

结论是没有结论. 中世界全空间扫完, 最高分只有 0.32 且平滑衰减, 完全没有断层.

排查过程花了很多轮: 怀疑过判据太松, 怀疑过尺度, 怀疑过内核有 bug, 甚至专门给每个偏移
做单独计时. 直到用户指出**地图是玩家后期改过地形的**, 整条路线才被判定为无效 ——
地图剖面对应的从来不是世界生成结果, 扫再久也不可能有解.

这一步的教训: 在排查"实现是否正确"之前, 先确认"输入是否对应问题".

## 阶段 3: 主画面路线

改用刚进游戏时的主画面截图. 一屏约 100 格, 分辨率 2034x550.

定标用了"地表高度必为整数"这条判据, 得到格宽 21.25 / 相位 10.62, 与草地带自相关的 21 格周期
互相印证, 当时看起来相当可靠. **这是后面最大的坑.**

## 阶段 4: 上 GPU

CPU 版每换一个偏移就要重跑模拟, 太慢. 于是写了 CUDA 版: 内核 A 每种子模拟一次并写出窗口,
内核 B 每 block 一个种子, 256 线程并行评估所有 偏移 x 尺度 组合.

期间修掉三个会让整条链路失效的缺陷:

- 内核 B 写死 `有效列数 < 200 则跳过`, 而主画面观测只有 74 列有效, 导致组合全被跳过, 候选恒为 0.
- 剖面缓冲存成整数, 与小数观测比较时残差抖动, 真种子命中率被砍半.
- 主机侧按发现顺序收集候选, 假候选瞬间打满上限, 高分种子被丢弃.

同时也发现: 候选数为 0 或"每批打满"这类现象, 都可能是配置问题而不是判据问题.

## 阶段 5: 多图拼接

用户陆续给了四张主画面截图 (移动位置后各截一张). 写了拼接工具: 逐张提取剖面, 在重叠区搜索
偏移与比例尺, 按偏移拼接, 重叠处取中位数.

正式使用前先用合成帧做了单元测试, 当场抓到一个符号错误 (把"前一帧起点减后一帧起点"当成
正向累加), 否则拼出来的长剖面会左右颠倒.

拼两张时发现: 两张各自定出的格宽差 4.7 个百分点 (21.25 与 22.25), 于是把比例尺纳入搜索.
两张的对齐一致率 94 个百分点, 重叠 33 格.

## 阶段 6: 用户直接量方块

虽然拼上了, 但结果依然定不了案. 用户提出做一个交互式页面自己调, 并给出了决定性的信息:
**他在游戏里量了 2x2 方块, 是 39 x 37 像素**, 也就是每格 19.5 到 20.86.

这直接推翻了自动定标. 换用 20.86 后: 台阶率从 0.0 个百分点恢复到 9 个百分点量级,
四张图两两重叠区误差降到 0.04 格.

期间还写了一个交互式校准页 (拖拽拼接 + 逐张调格宽相位 + 网格叠加), 让用户手工确认.

## 阶段 7: 人工标注

用户提出由他手工标注地表. 又写了标注页: 点击自动吸附到格子边界, 可标记 完整方块 / 斜坡两个方向 /
树木作废, 导出 JSON.

用户标注了 **249 列** (225 个完整方块, 24 个斜坡). 树木相关全部省略, 因为两张截图拍摄时间不同,
中间树被砍过, 树的位置反而不可靠.

## 阶段 8: 最后一个配置错误

用这份人工标注的剖面跑全空间, 榜首只有 0.9277 且与第二名几乎并列, 每批仍打满 100 条.

这次没有继续猜测判据, 而是先做了一件早就该做的事: **用已知种子造一份同列数的观测, 跑同样的搜索**.
结果直接是 **0 个候选** —— 而那个范围里确实包含真种子. 真种子拿 0 分只可能是配置错.

查日志里的窗口范围, 起点是 2898; 而正确值应当是 `3180 - 141 = 3039`. 差 141, 正是 marker 被减了两次.
内核的 `--spawn-lo` 参数含义是出生点的世界列, 代码内部会自行减 marker, 而我传了已减过的值.

修正后重跑对照: 真种子 **1.0000**, 假候选上限 **0.6145**, 间距 0.39.

## 阶段 9: 定案

用正确的参数重跑人工标注的 249 列剖面, 榜首:

```
seed = (种子已隐去)   spawn_x = 3198   scale = 1.00   score = 0.9518
```

模拟剖面与用户标注几乎全程重合, 分歧只集中在少数几列 (手工标注 249 列, 有十来列标偏属正常).
用户游戏内核对通过.

## 阶段 10: 龙蛋核查 (结论修正)

种子确认后, 用户指出主播世界里 (4157-4158, 662-663) 有一个 2x2 的龙蛋 (直接摆在地图上的物件), 而他生成的世界里没有.

**最初的错误推断.** 对比两份同种子存档的头部, 发现 `mushroom_bg` (22 / 76 / 68) 与 `underworld_bg` (214 / 97 / 228) 每次生成都不同, 于是推断"存在不随种子播种的随机数流, 多刷几次就能刷出龙蛋". 这个推断当时还有一个"证据": 两份 regen 的方块段相差 814 字节.

**那个证据是错的.** 用户指出其中一份 (`dev.wld`) 是他挖过的世界 —— 那份差异来自玩家改动, 不是生成.

**用批量实验证伪.** 用服务端命令行建世界:

```shell
TerrariaServer.exe -autocreate 2 -seed (种子已隐去) -evil 2 -difficulty 1 -world genN.wld
```

注意 `-evil 2` 是猩红, `-difficulty 1` 是专家; 少了这两个参数会生成随机邪恶与普通难度, 地形完全不同. 8 并发, 32 个世界 225 秒跑完.

```
32 个世界, 方块段 md5 全部 = 593c4606e9
32 个世界, (4157,662)(4158,662)(4157,663)(4158,663) 全部 = (5, 0, 5, 0)
方块段哈希种类: 1
```

**世界内容是确定性的.** 同一颗种子配同一套参数, 方块数据永远逐字节相同. 龙蛋不会因为重刷而出现 —— 这条路是死的.

**那两个变化的字段是什么.** `mushroom_bg` 与 `underworld_bg` 只是头部里的背景样式编号, 属于纯表现层, 不参与方块生成. 所以真实图景是分层的: 方块数据完全确定, 只有这几个表现层编号每次重新掷.

**顺带解释了一个细节.** `regen.wld` 的方块段与其余所有世界都不同, 而 `regen2` 与 32 个服务端生成完全一致. 合理解释是 `regen` 被打开过 —— 客户端在载入世界时会对出生点周围做一次落地清理并写回存档. 这从反面印证了"生成是确定的, 有差异的都是被改动过的".

**新增工具**: `tools/wld_tiles.py` 读取存档中任意格子的方块 ID (按列解码方块段的 RLE, 并用"游标是否恰好落在段边界"自检).


| 分支 | 结局 |
| --- | --- |
| Windows 机器上跑 CPU 版 | 弃用, 换成 Linux GPU 机器 |
| WSL 上跑 CPU 版 | 弃用, 同上 |
| 地图截图路线 | **作废**, 输入本身无效 |
| 地图浮空物修正版 | 作废, 同上 |
| 自动定标 (整数判据) | **作废**, 判据在平坦地形上失效 |
| 主画面单张 | 可用但分辨力不足 (74 列) |
| 主画面多图拼接 | 可用, 126 列 |

| 反复生成世界刷龙蛋 | **作废**, 实测世界内容完全确定性 |

## 最值得记住的两件事

1. **定标错误会伪装成"判据不够强".** 格宽偏 10 到 15 个百分点时, 真种子与假候选的分数差被抹平,
   于是每一轮都表现为"扫完了, 有一堆 0.9, 但没有断层". 识别方法是看台阶率这类**独立于搜索的**
   统计量.

2. **先跑已知种子的对照, 再跑全空间.** 全空间一轮要几十分钟, 而对照只要几秒. 真种子在自己的观测上
   拿不到满分, 就绝不要去看全空间的结果 —— 那只会让你去分析一个错误的分布.

3. **假设要用存档实测, 而不是靠更多次搜索.** 龙蛋这一轮, 我先推出"非确定性"假设, 又把"两份存档差
   814 字节"当成证据 —— 而那份证据其实来自玩家改动. 直到用服务端批量生成 32 次、直接比对区块段哈希,
   才拿到确定结论. 换一种做法, 一开始就去问"同一颗种子能否生成出不同世界", 这个假设几分钟即可证伪,
   不必绕这么大一圈.
