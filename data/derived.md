## 2. 换算比例

地图四角: (45, 7), (843, 7), (45, 230), (843, 230). 也就是地图区域 798 x 223 px.

- 世界为**中型**: 6400 x 1800 格
- 横向: 6400 / 798 = **8.0201 格/px**
- 纵向: 1800 / 223 = **8.0717 格/px**
- 交叉验证: 798 : 223 = 3.578, 6400 : 1800 = 3.556, 误差 0.6%, 说明是整幅等比缩放

换算公式:

```
tile_x = (px - 45) * 8.0201
tile_y = (py - 7)  * 8.0717
```

精度: 1 px 约等于 8 格, 所以边界标注偏 1 px, 结果就差 8 格.

## 4. 目前确定的核心结论

- **出生点约在 (3200, 343)**, 中世界. x 落在世界正中, 与源码里 `SpawnPoint` pass 从 `Main.maxTilesX / 2` 开始搜索的行为一致.
- 地表高度受 `TerrainPass` 的夹取规则约束, 中型世界 (H=1800) 大致落在 `0.17H` 到 `0.26H`, 即 306 到 468 之间, 观测值 343 落在区间内.
- 山丘样式由 `TerrainPass` 的 `TerrainFeatureType` (Plateau / Hill / Dale / Mountain / Valley) 决定, 世界中心 0.48W 到 0.52W 被强制为 Plateau, 0.45W 到 0.55W 不允许 Mountain 和 Valley. 所以"出生点两侧是山丘"属于规则产物, 区分度低.

## 5. 源码侧已落地的事实

- 每生成一个 pass 之前都会 `Main.rand = new UnifiedRandom(seed)` 重新播种 (`Terraria/WorldBuilding/WorldGenerator.cs:127`), 所以每个 pass 内部的第 n 次取数是绝对固定的.
- `WorldGen.genRand` 与 `GenBase._random` 都指向 `Main.rand`.
- 地牢颜色的决定点: `DungeonCrawler.SetupDungeonGenVarVariables` 的第一句 `genRand.Next(3)` (0 蓝 / 1 绿 / 2 粉), 位于第 2 个 pass 的最开头.
- 金字塔选址也在第 2 个 pass (`DunesAndPyramidLocations`).
- 空岛坐标在第 22 个 pass (`FloatingIslands`), 空岛宝箱内容按空岛序号写死 (序号 1 = 星怒), 前缀在填箱时 roll.
- Palworld 联动的巨型龙蛋 (`PalworldChilletEgg`, item 6142 / tile 752) 由 `PlaceChilletEggs` 放置, 调用点是靠后的 `DyePlants` pass; 数量按世界大小 6 / 9 / 12.
- pass 之前的初始化段 (WorldGen.cs 7210-7500) 有 28 处取数, 全部只依赖种子; `leftBeachEnd` 在 7469, `rightBeachStart` 在 7482.
- `UnifiedRandom` 已移植到 Python 并用社区仿射公式完成校验 (5 个种子 x 4 个序号全一致), 见 `tools/rng_probe.py`.

## 8. 2026-10-16 追加结论

### 每 pass 重播种 (关键机制)

`Terraria/WorldBuilding/WorldGenerator.cs` 的 `RunPass` 在调用每个 pass 之前执行
`Main.rand = new UnifiedRandom(this._seed);`. 因此:

- 每个 pass 内部的第 1 次, 第 2 次, 第 3 次取数都是绝对固定的序号, 与之前的 pass 无关.
- TerrainPass 的随机流是全新的, 只依赖种子和少量外部参数 (海沙边界, FlatBeachPadding).
- 这也解释了社区"种子 -> 第 n 随机数"的仿射公式为什么成立.

### TerrainPass 可独立模拟

TerrainPass (`Terraria/GameContent/Biomes/TerrainPass.cs`) 逐列决定地表高度:

- 初始 `num2 = H * 0.3 * (Next(90,110) * 0.005)`, `num3 = (num2 + H*0.2) * (Next(90,110)*0.01)`
- 每 `Next(5,40)` 列换一次地形特征 (Plateau / Hill / Dale / Mountain / Valley), Plateau 的持续长度还要乘 `Next(5,30)*0.2`
- 世界中心 0.45W 到 0.55W 禁止 Mountain 与 Valley, 0.48W 到 0.52W 强制 Plateau
- 内地区间夹取到 `[0.17H, 0.26H]` = `[306, 468]`, 海滩区夹取到 `[306, 0.23H]` = `[306, 414]`
- 每列还会 `while (Next(0,3) == 0)` 调整岩石层高度

外参: `FlatBeachPadding = 5` (Configuration.json 的 Passes.Terrain), `leftBeachEnd ∈ [320, 379]`.

### 性能实测

- Python 版: 单种子 3600 列约 **7.8 ms**
- 直推全空间 2^31: Python 单线程 193 天; 若换成 C 且快 50 到 100 倍并 8 线程, 约 **6 到 12 小时**
- 因为对齐未知时可以"生成到窗口起点就先比前几列, 不匹配立即丢弃", 实际耗时会远低于这个上限

### 尚未验证的部分

**统计一致性检查 (已做)**: 从 `scaled.png` 抽出的 658 列剖面原始粗糙度偏高 (相邻列高度差均值 1.43), 用中值滤波去掉树干尖刺后降到 0.48 到 0.52, 95 分位 2, 跨度 79 到 80 格. 模拟剖面同样统计为: 均值 0.25 到 0.32, 95 分位 1 到 2, 跨度 61 到 86 格. 两者量级一致, 说明"1 px 约等于 1 格"的假设与 TerrainPass 模型都不离谱. 但这只是统计上的相容, 不是逐点验证.

TerrainPass 的移植目前**没有经真实世界逐点验证**. 需要一个已知种子的实况对照:

1. 在游戏里新建世界: 中型, 专家难度, 猩红, 种子填一个固定值 (例如 123456)
2. 进游戏后按 M 打开地图, 缩放到和 `shots/scaled.png` 相近的级别, 截图
3. agent 用模拟器算出同种子的剖面, 与该截图对比

只要这一步对得上, 整条流水线成立; 对不上就说明移植有细节错误, 需要逐段排查. 同时这一步也能反过来标定 `scaled.png` 的每格像素数.


| leftBeachEnd | 中心窗口 [2700,3400) 逐格相等 | 全球逐格相等 |
| --- | --- | --- |
| 362 | **63.7%** | 45.7% |

由此确定的两件事:

1. `tools/wld_surface.py` 可以当作**任意种子的真值来源**, 后面写 C 版扫描时用它对拍.
2. dev1 的 `leftBeachEnd` 约等于 362 到 364, 与我推算的取值区间 [320, 379] 一致.

### 两个踩过的坑 (初始化段的隐藏取数)

1. `RandomizeCaveBackgrounds` 的**分支之后**还有 3 次取数 (`iceBackStyle` / `hellBackStyle` / `jungleBackStyle`), 漏了会让整条流偏移 3 次.
2. `RandomizeWeather` (7277) 会取 `Next(10,200)` 再循环取 `NextDouble + Next(2)`.

### GPU 结论 (有数据)

在 RTX 4060 Laptop 上把模拟器写成 CUDA, 单偏移跑 2000 万种子:

| 版本 | 耗时 | 吞吐 |
| --- | --- | --- |
| local memory 版 | 86 秒 | 23.3 万种子/秒 |
| shared memory 版 | 88 秒 | 无提升 |

原因: `UnifiedRandom` 是**串行依赖链** (每次取数依赖上一次的 56 个 int 状态), GPU 的 3072 条通道都在等延迟. 而 16 核 CPU 的 9.7 万种子/秒 已经包含"每种子 81 个偏移 x 3 个尺度"的筛选. 所以这个任务 GPU 不划算, 决定用 CPU 跑.

另外 CUDA 版还有个待修的细节: 设备端的 `setup_beach` 对种子 123456 算出 left=357 (正确 364), 说明设备端浮点在某个分支上与 x86 不一致, 但因为 GPU 方案已被否决, 没有继续追.

### 交错推进尝试 (失败)

思路: 随机数是串行依赖链, 让一个线程同时推进 N 个种子的链, 用乱序执行盖住延迟.
实测 (Mac 8 线程, 300 万种子, 21 偏移 x 1 尺度):

| 交错数 | 用时 | 候选数 |
| --- | --- | --- |
| 1 | 92 秒 | 47 |
| 2 | 103 秒 | 48 |

不但没有加速, 候选数还变了 1 个, 说明改变循环结构后编译器做了不同的浮点优化 (FMA 收缩之类), 破坏了逐位一致性. 因此放弃交错, 保留原始版本的扫描.

### 结论: 时间几乎全在模拟上

单偏移 500 万种子与 81 偏移 x 3 尺度 500 万种子的耗时接近, 说明匹配开销可以忽略, 瓶颈就是每种子约 1.06 万次取数的串行链. 现有配置已接近该算法在这台机器上的极限.

### 噪声容忍度与"能不能认出真种子"

用 dev1 真值剖面当基准 (真种子 123456), 人为加三种噪声, 再扫 0..3M 看真种子还能不能排第一:

| 噪声档 | 噪声内容 | 真种子 C 分 | 排第一? |
| --- | --- | --- | --- |
| 干净 | 无 | 0.695 | 是 |
| 轻 | 30% 列抖 +-1, 5% 列抬升 4 | 0.695 | 是 |
| 中 | 45% 列抖 +-2, 10% 列抬升 6 | 0.565 | 是 (第二名 0.510) |
| 重 | 60% 列抖 +-3, 18% 列抬升 9 | 0.474 | 否 (掉到假候选之下) |

"抬升"模拟的是树冠: 地图上树冠在土表之上, 抽剖面时会把它当成地表, 于是观测值比真实地表高.

中噪声档下再复核一遍 (Python, 多尺度 x 全偏移, 纵向偏移取残差中位数):

| 指标 | 真种子 | 最好的假候选 |
| --- | --- | --- |
| 全列命中 (残差 <= 1.5 格) | 58.5% | 51.0% |
| 截尾命中 (丢掉最差 30% 列) | 80.2% | 71.5% |
| 逐格命中 (残差 <= 0.5 格) | **39.0%** | 24.2% |

结论: **逐格命中率是最可靠的判据** (间隔 15 个百分点), 因为它对"少数列被树冠抬高"不敏感.

### 工具里踩过的坑

1. `load_obs` 原本在参数解析**之前**执行, 导致 `--obs` 完全不生效 (噪声测试第一版全部读的还是真观测).

### 剖面抽取的判据交叉验证

整条链路里唯一无法用存档验证的输入就是"从截图抽地表剖面", 所以换两种独立判据重抽一次作对照:

| 判据 | 与所用剖面的中位差 | 完全一致 | `|差|<=1` |
| --- | --- | --- | --- |
| 最长天空段 (实际使用) | +0.0 | 71.8% | 85.4% |
| 首个"非天空非黑"缺口 | +0.0 | 70.6% | 84.3% |
| 自下而上找土体上缘 | +2.0 | 3.9% | 11.8% |

前两种合理判据互相吻合 (中位差为 0). 第三种在这个场景下不成立: 它找到的是土体下缘而不是地表.

### 覆盖性证明: 扫描区间 [0, 2^31) 等同于全部可能的种子

.NET 的 `Random(int seed)` 对负数取 `abs` (即 `-x` 与 `x` 得到同一条流), 因此负种子与对应的正种子生成完全相同的世界. 实测:

| 种子 | leftBeachEnd | rightBeachStart | WorldId |
| --- | --- | --- | --- |
| 123456 | 364 | 6074 | 1357784955 |
| -123456 | 364 | 6074 | 1357784955 |
| 2147483647 | 357 | 6049 | 2137491580 |
| -2147483648 | 357 | 6049 | 2137491580 |

结论: 扫 [0, 2^31) 不会漏掉任何可能的种子, 包括负数与 int 边界值.

### 出生点搜索范围是否够宽 (够)

回退搜索代码 (WorldGen.cs 约 16446 起):

### 用粗糙度转折判断世界大小 (未成立, 负面结果)

思路: 中心强制平台区的边界在 0.48W, 换算成相对出生点左侧的距离 —— 小世界 84 格 (第 387 列), 中世界 128 格 (第 343 列), 大世界 168 格 (第 303 列). 平台特征是低频漂移 (1/7 概率走一步), 区外是高频随机特征, 因此粗糙度应当在边界处转折.

实测分段 (|Δ| >= 2 的比例):

| 列区间 | 200-250 | 250-303 | 303-343 | 343-387 | 387-430 |
| --- | --- | --- | --- | --- | --- |
| 比例 | 0.0% | 3.8% | 10.0% | 2.3% | 16.3% |

三种假说都不相容 (无论边界设在 303 / 343 / 387, 都会落在"应当平滑却粗糙"的区间里).

**失败原因**: 387~430 段内部其实极平 (x 约 400~425 恒为 97), 粗糙度全部来自它两端的陡坎 (130 → 97 → 141). 分段统计把陡坎计入段内, 把"内部平坦"误读为"粗糙". 判据的分辨力被实现方式吃掉了.

**结论**: 世界大小这一前提仍然只能依据用户的明确说明. 可以部分证伪的是: 出生点右侧存在 >= 109 列的平缓段, 对小世界 (平台右边界仅在 +84) 不利, 与中世界、大世界相容.

### 搜索分数与复核指标是否等价 (基本等价, 个例有 0.03 差异)

用 12 个真实候选对比 C 扫描器的分数与 Python 复核的全列命中率:

| 项目 | 值 |
| --- | --- |
| 平均绝对差 | 0.0051 |
| 12 个中差值为 0 的 | 11 个 |
| 最大差异 | 0.0339 (seed 1746967394: C 0.503, Python 46.9%) |

**机制**: 两者估计纵向偏移的方式不同. C 用 ±3 格的直方图投票 (取众数), Python 用残差中位数. 残差分布对称时二者给出相同偏移, 于是分数完全一致; 分布偏斜时 (例如被树冠抬高的列占比偏高) 众数与中位数分离, 出现零点几的差异.

**为何不影响判定**:

1. 0.034 远小于真种子与最好假候选的间隔 (噪声实验中为 0.055)
2. 复核以逐格命中率为准, 该指标在噪声实验中的间隔是 15 个百分点 (39.0% 对 24.2%)
3. 复核独立搜索全部 5 个尺度, 不受 C 侧记录的是哪一个尺度影响

### 结果落盘时机 (已修)

原实现只在"刷新全场最好成绩"时写 `data/candidates_top.txt`. 隐患: 如果真种子出现时它不是全场最高分 (例如上面压着一个 0.54 的假候选), 它就不会立即落盘, 要等到下一次有人刷新记录才被带出去; 若期间进程被杀, 这条结果就丢了.

已改为三条路径都会落盘:

1. 刷新全场最好成绩时 (原有)
2. **每 60 秒无条件写一次** (新增定时线程)
3. 扫描收尾时写一次 (新增)

验证: 用 `--offer 0.99` 跑一遍 100 万种子 (保证一个候选都不会产生, 因此旧的"刷新记录"路径绝不会触发), 文件依然被写出, 内容为表头 "当前共 0 个" —— 证明定时/收尾路径生效. 同时 `--check` 输出与改动前逐值一致, 计算未受影响. 大世界与小世界版本也已同步重编.

### 快筛与完整评分的偏移估计是否一致 (一致)

审计动机: 若两者用不同的偏移估计, 快筛可能在某个偏移下把种子判死, 而完整评分本可在另一个偏移下救回 —— 这就是不可见的假阴性.

| 项目 | quick_score | score_alignment |
| --- | --- | --- |
| 偏移估计 | 5 个锚点取中位 | 5 个锚点取中位 |
| 锚点位置 | 按等距列号取样 (obs_n/5) | 按有效列序号取样 (第 t 个有效列的 1/5) |
| 打分范围 | 每 13 列取 1 | 全部有效列 |
| 容差 | 2.0 | 1.5 |

结论: 偏移估计同源 (5 锚点中位), 不存在"快筛判死、完整可救"的机制. 唯一差异是锚点落点, 可能带 ±1~2 格偏移差, 而真种子快筛得分 0.737 / 0.763 对下限 0.40 有近一倍余量, 动不了它.

这也解释了此前测得的"搜索分数与复核全列命中率平均只差 0.005": 两边都是中位类偏移估计, 本就应当几乎相同.

### 三种噪声档下真种子的排名 (修正此前一个错误结论)

此前我以为"重噪声下真种子的分数会掉到假候选之下", 依据是把它与轻/中档测得的假候选天花板 (0.53) 相比. 这是**错的**: 噪声同时压低真种子与假候选的绝对分, 因此排名关系得以保留.

实测 (同一份 dev1 真值观测, 各自加噪后扫 0..300 万):

| 噪声档 | 真种子 C 分 | 最好假候选 | 真种子排名 | 间隔 |
| --- | --- | --- | --- | --- |
| 中 | 0.5651 | 0.510 | 第 1 | 0.055 |
| 重 | 0.4742 | 0.4510 | 第 1 | 0.023 |

真正的风险不在排名, 而在 **offer 阈值**: 重噪声下真种子的绝对分只有 0.474, 而远端原用 offer 0.50 —— 那样它连进入候选榜的机会都没有.

因此把恢复流程的 offer 从 0.50 改为 **0.42** (落盘上限同时提升到 4096, 等于内存中保留的全量). 处置策略:

- 老进程还活着 → 让它跑完 (offer 0.50 的版本, 对轻/中噪声档足够; 真种子在这两档都是第一名)
- 老进程已死 → 用新版本以 offer 0.42 重启 (含断点续跑, 未来再休眠也只损失 5 秒)
- 老进程跑完但结果平庸 → 用 offer 0.42 重跑

### 判定判据按实测重校准 (截尾命中率在重噪声下失效)

重噪声档下把 65 个候选送进复核 (逐格 = 残差 <= 0.5 格的列占比):

| 种子 | C 分 | 逐格 | 截尾 | 全列 |
| --- | --- | --- | --- | --- |
| 123456 (真) | 0.474 | **31.7%** | 63.1% | 49.4% |
| 最好的假候选 | 0.451 | 20.5% | **64.0%** | 43.5% |

关键发现: **截尾命中率在重噪声下失去分辨力** —— 有假候选拿到 64.0%, 比真种子的 63.1% 还高. 而原来的判定里有一条"截尾 >= 75%", 会把重噪声下的真种子误判为"证据不足".

逐格命中率的表现则相反: 真 31.7% 对假 20.5%, 间隔 11.2 个百分点.

据此重写判据 (全部有实测依据):

| 判据 | 阈值 | 依据 |
| --- | --- | --- |
| 逐格命中率 | >= 28% | 真种子 中 39.0% / 重 31.7%; 最好假候选 24.2% / 20.5% |
| 交叉观测逐格 | >= 25% | 同上, 留出观测版本差异的余量 |
| spawn_x 范围 | 3190~3210 | 出生点实际为 3200 ± 5 |

截尾命中率降级为仅展示. 双向验证: 重噪声真种子 3/3 通过 (最坏情况), 真实观测下的错误种子 0/3.

### 1 像素 = 1 格 的确认, 以及一个重要的难度推论

判据: 相邻列的跳变比例. 若截图是被压扁过的地图 (例如 0.5 像素/格), 台阶密度会翻倍.

| 剖面 | `|Δ|>=1` | `|Δ|>=2` |
| --- | --- | --- |
| 观测 (用户截图) | 25.0% | 6.6% |
| dev1 真实地表 (存档解析, 同窗口) | 26.2% | 3.3% |
| 随机种子的模拟剖面 | 13.9% ~ 18.6% | 1.7% ~ 4.6% |

观测值贴近真实地表的 26.2%, 远离"压扁"情形应有的 70% 以上, 因此 1 像素 = 1 格 成立.

**推论**: 真实地形比我模拟的更碎, 因为存档中的地表还包含后续 pass 铺设的土石与挖出的洞穴, 它们会额外制造台阶; 我的模拟只到 TerrainPass 为止, 因此偏平滑.

含义: 对真实观测的难度应参照"中噪声档"估计 (真种子约 0.55~0.65), 而不是乐观的 0.695. 即便如此仍高于假候选天花板 (0.53) 与 offer 阈值. 这也说明中噪声模型是贴近现实的, 而非过度悲观.

### 额外台阶会不会造成持续漂移 (不会, 噪声模型有效)

疑虑: 真实地形的台阶比模拟多约 9 个百分点, 若这些额外台阶是"地形高度"的改变, 观测与模拟的相对偏移就会随列号累积, 到窗口后半段彻底失配 —— 那样局部尖峰型的噪声模型就是过度乐观的.

查证: 额外台阶是**局部且可回退**的. 理由如下.

- 存档里的"地表"定义为每列自上而下第一个实体方块. 后续 pass 铺草、铺土、铺沙只是在**替换**表层方块, 不改变其高度.
- 真正额外制造台阶的是树、植物、裸露矿脉这类**立于地表之上**的东西, 它们只影响所在的那几列.
- dev1 的逐格对照佐证: 63.7% 逐格相等, 且 72.1% 的偏差在 ±1 格以内 —— 是局部扰动而非累积漂移.

结论: 中噪声模型作为真实观测难度的估计是站得住的, 预期真种子得分 0.55~0.65.

### 对照图的判读方式 (图正确, 但目视描述不可靠)

对重噪声档真种子的对照图做了数值核查:

| 项目 | 值 |
| --- | --- |
| 拟合偏移 | 0.0 (合成观测本身就是模拟剖面, 正确) |
| 残差中位 | +0.00 (两曲线整体对齐) |
| 残差分位 | 5% -4, 25% -1, 50% 0, 75% +3, 95% +8 |
| `|残差|<=0.5` 比例 | 31.7% (即图中的 exact) |

视觉模型把这张图描述为"红线在上、蓝线在下、各走各的", 与数值不符: 残差中位为 0, 整体是对齐的, 只是每点散布达 -4~+8 格. 在散布这么宽的散点图上, 目视很容易读成两条分离的带.

另外发现一个真实数据特征: 前 200 列残差中位 +3, 后 200 列为 0 —— 左段存在系统偏移, 但这是合成噪声模型 (尖峰抬升集中在左段) 的产物, 与真实观测无关. 绘图如实反映了它.

**结论**: 对照图保留在证据链里作为形状直观展示, 但判读必须以数值指标为准, 不采信对图形的目视描述.

### C 与 Python 两套 TerrainPass 实现是否一致 (逐格一致)

审计动机: C 扫描器负责搜索, Python 工具负责验证与判读. 若两者的地形模拟有偏差, C 排出的第一名用 Python 复算时可能评分很低, 会被误判为"证据不足" —— 这条不一致会同时污染搜索与验证两端.

实测 (7 个种子, 对照窗口 2700~2760 共 60 格):

| 种子 | 结果 |
| --- | --- |
| 123456 / 1 / 2 / 2147483647 / 999999999 / 0 / 12345 | 全部逐格一致 |

**操作教训**: 第一次比较用字符串对比, C 打印整数 (`412`) 而 Python 打印浮点 (`412.0`), 于是 7 个种子全报"不一致". 这是同一天内第二次被格式差异误导 (前一次是 `--check -- -123456` 被解析成种子 0). 此后凡数值对照一律先做数值解析.

### 探活作业升级为两阶段 (bash-2292)

原版本只负责"链路恢复后把扫描接上", 接上就退出, 之后扫描跑完无人知晓.

新版两阶段:

- 阶段一: 每 3 分钟试一次 ssh. 一旦连通 —— 老扫描进程还活着就让它跑完; 已死则 scp 最新源码、远端编译三个尺寸版本、以 `--offer 0.42 --resume` 重启.
- 阶段二: 每 5 分钟查一次扫描进程数与候选榜首. 一旦出现得分 >= 0.55 的候选, 或扫描进程结束, 立刻打印进度与榜首并退出.

这样机器醒来的全过程 (恢复扫描 → 跑完/出结果) 都不需要我主动轮询, 我在被唤起时读它的输出即可. 阶段二最长 8 小时.

### 避免重复扫描: --skip-blocks

远端扫描冻结在 22.4%, 但它的覆盖范围不是"全空间的前 22%", 而是**每个线程各自区间的前 22.4%**: 16 个线程各跑满 3000 万种子, 合计 4.8 亿.

本地兜底是 8 线程, 区间划分不同, 于是会把远端已扫的部分再扫一遍, 白费约 5 小时.

新增参数 `--skip-blocks <区块大小> <跳过长度>`: 跳过每个区块开头指定长度的种子. 用远端的线程区间 134217728 (= 2^31/16) 作为区块, 跳过每块前 2800 万 (远端实际扫了 3000 万, 留 200 万安全余量 —— 远端各线程速度一致, 进度差异远小于 1%, 余量充足).

验证:

| 场景 | 用时 |
| --- | --- |
| 完整扫 300 万种子 (4 线程) | 3 分 18 秒 |
| 跳过每 100 万的前 90 万 (实际扫 30 万) | **24 秒** |

快 8.2 倍, 与实际只扫 10% 相符. 不传该参数时 `--check` 输出与改动前逐值一致, 计算未受影响.

本地兜底随即改用该参数重启, 只补远端未覆盖的部分.

### 一个两条路都会漏掉的盲区 (已修)

问题: 远端已经扫过的 4.8 亿种子是用 **offer 0.50** 的旧版本扫的; 新加的本地兜底用 `--skip-blocks` 恰好跳过这段. 如果真实观测偏脏 (真种子得分落在 0.42~0.50), 而真种子又正好落在那 4.8 亿里, 则**两边都不会记录它**.

发生概率: 真种子均匀分布, 落在该区间的概率 22.4%; 再乘上"得分低于 0.50"的概率 (重噪声档下约 20~30%), 合集约 5~7%. 不大, 但属于会让人白等一整天的类型.

修正后的恢复流程:

1. **先抢救老进程的候选文件** (scp 到本地 `data/candidates_remote_frozen.txt`) —— 它记录了那 4.8 亿里所有 >= 0.50 的候选, 可能直接就是答案
2. 停掉老进程 —— 它的 offer 0.50 是漏检来源
3. 部署新版本并以 `--offer 0.42` 全空间重启. 注意重启后各线程从自己区间开头开始跑, 而区间开头正是旧进程覆盖的部分, **因此盲区会在重启后的第一个小时内自然被补上**, 不需要特殊处理
4. 阶段二盯结果

本地兜底保持不变 (跳过远端已覆盖段), 与远端重启后的全空间扫描形成互补.

### 候选密度随扫描区间变化 (观察记录, 无害)

| 数据来源 | 扫描量 | >= 0.50 候选数 | 密度 |
| --- | --- | --- | --- |
| 远端 (offer 0.50) | 4.8 亿 | 12 | 1 / 4000 万 |
| 本地 (offer 0.42) | 2000 万 | 7 | 1 / 290 万 |

相差 14 倍, 按泊松估算偏差约 10σ, 不是统计涨落. 已排除实现差异: 本地重扫时复现了远端榜单中的同样种子与同样分数 (`270079926` 0.5276, `538285369` 0.5152, 逐位相同).

最可能的解释是**地形相位**: leftBeachEnd 决定出生点附近的山丘/谷地形态, 某些相位的地形本身偏平缓, 与同样偏平缓的观测剖面更容易碰巧对上. 远端样本跨约 150 个相位会平均掉该效应, 本地这 2000 万只跨约 6 个相位, 恰好落在高密度区间.

**不影响判定**: 候选增多只会让榜单更拥挤, 无法制造出 0.55 以上的假候选 (噪声实验已证明假候选天花板在 0.51~0.53). 记录在此, 避免将来看到候选总数远超预期时误判为计算错误.

### 候选数组容量: 4096 -> 65536 (修掉一个会丢答案的隐患)

推算: 本地 2000 万种子里 >= 0.46 的候选有 264 个, 线性外推到全空间 21 亿约为 **2.8 万个**. 而候选数组只保留最好的 4096 个.

若真实观测偏脏 (真种子得分约 0.474, 见重噪声实验), 它就会排在这 2.8 万个假候选之后, **被挤出数组** —— 扫描跑完却拿不到答案, 而且没有任何报错提示.

修改:

| 项目 | 原值 | 新值 |
| --- | --- | --- |
| 内存保留 (TOPK) | 4096 | 65536 |
| 落盘条数 | 4096 | 8192 |
| 落盘排序 | 选择排序 O(n^2) | qsort O(n log n) |

保留 65536 条意味着即使真种子只有 0.47, 压在其上的约 2.8 万条也进不了保留上限之外. 代价是替换操作从 O(4096) 变 O(65536), 但候选到达速率约每秒 6 条, 合每秒 40 万次运算, 相对每秒 2.8 万种子的模拟开销可忽略.

验证: 与改动前 `--check` 输出逐值一致 (计算未受影响); 三个尺寸版本均已重编.

### 落盘上限也要跟上 (8192 -> 65536)

上一步把内存保留提到 65536 后, 落盘仍写 8192 条 —— 而实际能读到的只有文件. 如果真种子 (重噪声下 0.474) 排在约 9000 名, 它在内存里活着却不会出现在文件里, 等于容量白扩.

已把落盘上限改为 TOPK (写满保留数组), 文件约 2.6 MB, 每 60 秒重写一次 (qsort 排序约百万次运算, 写入约 50 ms), 开销可接受.

验证: `--check` 输出与改动前逐值一致; 三个尺寸版本已重编; 本地扫描第三次重启 (断点续跑, 进度无损).

## 关键决策: 搜索排序指标从 C 分改为逐格命中率

### 触发原因

复核真实观测下抢救回来的 428 个候选时发现: **C 分数与逐格命中率几乎不相关**. C 分最高的 0.538 逐格只有 15.7%, C 分 0.519 的反而是逐格最高的 24.6%.

后果: 若真实观测偏脏 (真种子 C 分 0.474), 按 C 分排序复核前 100 名找不到它, 需要复核上万名 (约四小时).

### 实测依据

真实观测下用逐格指标 (容差 0.5) 扫 200 万种子, offer 0.10:

| 项目 | 值 |
| --- | --- |
| 候选数 | 1463 |
| 榜首 | 0.2709 |
| 紧随其后 | 0.2513 / 0.2353 / 0.2317 / 0.2299 / 0.2282 |

即真实观测的假候选逐格上限约 **0.27**, 而真种子的逐格命中率在噪声实验中为 31.7%~39.0%. 换成逐格排序后, 真种子会排在所有假候选之上.

### 执行

远端以 `--tol 0.5 --offer 0.20 --quick 30 --cols 3550` 全空间重启 (此前刚跑 3 分钟, 切换成本近乎为零), 并删除断点文件强制重扫 (断点只记录位置, 不记录候选, 若续跑会跳过旧指标扫过的区域, 从而漏掉真种子).

守望作业的触发线同步从 C 分的 0.55 改为逐格指标的 0.30.

### 真种子在真实观测下的逐格命中率预期 (上调)

此前的 31.7%~39.0% 是用**加噪**合成观测测出的 (对 dev1 真值加轻/中/重三档噪声). 真实观测更像哪一档, 需要独立判断:

- 真实观测的台阶密度 25.0%, 与真实地形的 26.2% 几乎相同 (若被压扁或严重失真, 会显著偏离), 说明提取质量较高
- dev1 对照显示模拟剖面与真实存档地表有 63.7% 的列逐格相等
- 但提取过程本身有 1~2 格的量化误差, 逐格指标要求残差 <= 0.5 格 (即整数级匹配), 这部分误差会拉低命中率

综合估计真种子在真实观测下的逐格命中率约 **40%~55%**, 高于实测假候选尾部 (200 万样本时 0.27, 全空间可能爬到 0.32~0.35). 判定空间清晰.

### 搜索指标与复核指标的平价验证 (发现 6 个百分点的个例差异)

切换远端到逐格指标后, 对同一批候选比较两端数值:

| seed | C 端分数 | Python 逐格 | 差 |
| --- | --- | --- | --- |
| 269817533 | 0.2923 | 28.9% | 0.3 |
| 134415589 | 0.2763 | 27.5% | 0.1 |
| 1745683927 | 0.2745 | 27.1% | 0.4 |
| 1073923980 | 0.2888 | 22.8% | **6.0** |
| 1880405947 | 0.2727 | 21.7% | **5.6** |

原因: 两端估计纵向偏移的方法不同. C 端为速度只取 5 个锚点的中位; Python 端取全部有效列残差的中位. 容差 1.5 时该差异只值 0.005, 容差 0.5 时指标对偏移极度敏感 (偏一格丢掉大批列), 差异放大到 6 个点.

对策:

- 排名仍可信: 差异对真种子与假候选同向, C 端第一名依然最值得复核
- 对外报数一律用 Python 端的值 (偏移估计更稳健)
- 定案以 Python 复核为准, C 端只作警报

补充: 若要彻底消除该差异, 需把 C 端的锚点数从 5 提到 20 以上 (成本很低), 但会改动评分逻辑并需要重跑, 收益仅在于"少复核一些候选", 故暂不做.

### C 端排序与 Python 端排序的相关性 (0.51, 决定复核范围)

对远端逐格指标下的前 30 名做双向比较:

| 项目 | 值 |
| --- | --- |
| C 名次与 Python 名次的相关系数 | +0.509 |
| 两端逐格值最大差 | 0.173 (17 个百分点) |
| Python 逐格最高的候选 | C 端第 1 名 (28.9%) |
| Python 前 8 名的 C 端名次 | 1 / 3 / 4 / 15 / 11 / 7 / 13 / 24 |

根因同前: C 端为速度只取 5 个锚点估计纵向偏移, 容差 0.5 时该估计的偏差被放大.

关键性质仍然成立: 容差 0.5 下真种子与假候选差距大 (0.40~0.55 对 0.22~0.29), 即使排序被扰动, 好候选也不会掉出很靠前的位置 —— Python 眼中的前 8 名全部落在 C 端前 25 名内.

据此把最终复核范围从前 100 名扩大到**前 1000 名** (约 25 分钟).

不改 C 端偏移估计的理由: 把锚点数从 5 提到 20 以上虽能把复核范围缩回 50 名, 但需改动核心评分逻辑并重启扫描, 在临近出结果时引入 bug 的风险大于 20 分钟的收益.

## 第三台机器 (远端 GPU 主机) 与 GPU 复测

用户提供的机器: 40 核 AMD EPYC 7663, 156 GB 内存, 两张 RTX 4090, CUDA 12.8.

### CPU 基准 (实测)

500 万种子 / 28.4 秒 (40 线程, 3 尺度 x 81 偏移) = **17.6 万种子/秒**, 是 WSL 那台 (9.3 万/秒) 的 1.9 倍.

跨机器一致性: 同一份代码在 EPYC 上 `--check 123456` 得到 leftBeachEnd 364 / rightBeachStart 6074, 与 WSL 上逐位相同.

### GPU 复测 (用户要求)

CUDA 版 (`tools/sweep.cu`) 在 RTX 4090 上跑 2000 万种子, 逐偏移推进:

| 项目 | 数值 |
| --- | --- |
| 每个偏移耗时 | 约 5.6 ~ 6.4 秒 |
| 81 个偏移总计 | 约 7.6 ~ 8.6 分钟 (仅 1 个尺度) |
| 等效吞吐 | 约 3.9 ~ 4.4 万种子/秒 |

对照: CPU 在同等工作量 (1 个尺度 x 81 偏移) 下约 19 万种子/秒.

**结论: GPU 比 CPU 慢约 4.5 倍.** 原因是 CUDA 版每个偏移独立跑一遍, 每个种子被重复模拟 81 次; CPU 版每种子只模拟一次, 然后从这个剖面算出 81 个偏移的得分. 地形模拟是全部开销所在, 所以这个差别是决定性的.

补充: 理论上可以改写 CUDA 版让每种子只模拟一次 (3550 列的剖面约 14 KB, 能放进共享内存), 但那是重写而非调参, 而 CPU 路线已经用两台机器在跑, 不值得现在动.

## GPU 版重写 (两个 kernel) 与实测

### 结构

旧版: 每个横向偏移一个 kernel, 每个种子被完整重新模拟 81 次.
新版: 拆两个 kernel.

1. `profile_kernel`: 每线程一个种子, 模拟一次, 把覆盖所有偏移与尺度的列窗口 (758 列) 写进全局缓冲
2. `score_kernel`: 每种子一个 block, 剖面进共享内存, 256 线程分摊 81 偏移 x 3 尺度 = 243 个组合, `atomicMax` 归并出每种子最佳组合

### 实测

| 项目 | 数值 |
| --- | --- |
| 吞吐 | 200 万种子 / 2.3 秒 = **约 90 万种子/秒** |
| 相对旧 CUDA 版 | **20 倍** |
| 相对 40 核 CPU | 5 倍 |

### 判据对齐 (关键)

新版最初用"众数偏移 + 相邻三箱求和", 实际等价于 ±1.5 松判据; 与 CPU 的紧判据 (中位偏移 + 容差 0.5) 完全不同, 候选集合重合只有 1.4%.

改成**中位数偏移 + 单箱计数**后与复核口径一致. 同一候选的三方对比:

| 度量 | 种子 118926 |
| --- | --- |
| GPU 新版 | 25.85% |
| Python 逐格 | 24.1% |
| CPU 的 `--check` | 41.2% (= Python 全列 43.9%, 松判据, 口径不同) |

注: CPU 的 `--check` 便利路径不受 `--tol` 影响, 恒为松判据; 搜索路径则正确响应 `--tol`.

### 名次相关性

GPU 分数与 Python 逐格在前 60 名内的名次相关系数只有 +0.063. 原因是这批候选分数全部挤在 22%~24% 的窄带内, 窄带内部排序本身是噪声. 真种子预期 31%~40%, 会以明显分差排在假候选之上, 因此流程成立: GPU 快速筛出窄带, Python 复核重排.

### 修掉的截断

候选上限原为 2 万, 按实测密度全空间约 12.6 万条, 超出部分按发现顺序丢弃 (晚出现的高分种子会被扔掉). 已改为 50 万.

### 新 GPU 版的端到端验证 (用已知答案的合成观测)

合成观测由 dev1 世界生成, 因此"真种子"已知是 123456. 让新版 GPU 扫含它的小区间:

```shell
./sweep2 data/synth_obs.txt --range 123000 124000 --tol 0.5 --offer 0.30 --batch 400000 --device 0
```

结果: 1000 个种子里**只有一个**越过阈值

```
seed=123456  spawn_x=3197  scale=1.00  score=0.6043
```

真种子得分 0.6043, 其余全部低于 0.30, 且报出的 spawn_x=3197 与尺度 1.00 都与已知真值一致.

这条验证覆盖了 `--check` 未覆盖的新 kernel 路径 (剖面只算一次 + 243 组合并行), 证明拆分没有破坏正确性.

校准推论: 真实观测下真种子的 GPU 得分应落在 0.42~0.57 (GPU 判据比 Python 逐格高约 1.7 个点, 而 Python 逐格预期 0.40~0.55), 与假候选窄带 0.26 之间差距很大.

### 判定门槛按实测上调 (28% -> 35%)

真实观测下假候选的逐格命中率会随样本增大而上爬: 早先测得的 24.6% 是在较小样本上得到的, 而 CPU 兜底扫描到更广范围后, 榜首的逐格已达 **28.7%** —— 原门槛 28% 会被假候选通过.

按合成用例给出的对比 (真种子在自身观测上逐格 60.4%, 假候选带 25%~29%), 门槛上调为:

| 判据 | 旧 | 新 |
| --- | --- | --- |
| 逐格命中率 | >= 28% | **>= 35%** |
| 交叉观测逐格 | >= 25% | **>= 30%** |

双向回归:

| 用例 | 逐格 | 交叉观测 | spawn | 结论 |
| --- | --- | --- | --- | --- |
| 合成真种子 123456 | 60.4% | 60.4% | 3197 | 3/3 通过 |
| 真实观测当前榜首 1596162502 | 28.7% | 22.1% | 3195 | 1/3, 证据不足 |

新门槛放行真种子且挡下真实观测中最强的假候选, 余量 6 个百分点.

## 观测来源的转折: 地图作废, 改主画面

### 地图观测从根本上无效

用户指出地图是**后期改过地形**的截图. 因此地图剖面对应的不是世界生成结果, 基于它的全部搜索
(v1 的 658 列观测, v2 浮空物修正版, 以及 CPU 上跑的所有轮次) 原理上不可能命中 —— 这解释了
此前"中世界全空间 21.5 亿种子扫完、最高分只有 0.32 且平滑衰减"的现象.

### 主画面观测的建立

改用游戏主画面截图 (刚进入世界, 玩家站在出生点). 好处是方块清晰, 不存在地图上"云被当成地表"的问题.

格宽不靠猜, 用一条客观判据定: **真实地表高度必然是整数格**, 因此取使提取剖面最接近整数的那组参数.
结果 21.25 px/格 (相位 10.62), 到整数格偏差 0.042 格; 其他候选格宽是 0.14~0.39.
这与草地带自相关的 21 峰、以及"玩家站立占 3 格"推出的 22 相互印证.

剖面: 95 格中 74 格有效, 21 格 (树冠) 按"比邻居高一格以上"剔除.

### 修掉的三个缺陷 (都会让这条链路完全失效)

| 缺陷 | 后果 | 修法 |
| --- | --- | --- |
| kernel B 的 `if (cnt < 200) continue` | 74 列观测每个组合都被跳过, 候选恒为 0 | 下限改 20 |
| 剖面缓冲存 `(int)num2` (整数) | 观测有小数精度而模拟没有, 真种子命中被随机截断掉一半 | 两侧统一量化到 1/8 格 |
| 主机侧按发现顺序取前 MAX_OUT 条 | 假候选瞬间打满上限, 之后出现的高分种子被丢弃 | 每批只保留得分前 100 名 |

### 端到端验证 (用已知种子造同格式观测再让 GPU 搜)

```
seed=123456  spawn_x=3200  scale=1.00  score=1.0000    <- 真种子, 唯一满分
seed=123645  spawn_x=3201  scale=0.97  score=0.7027
seed=123263  spawn_x=3202  scale=1.00  score=0.7027
```

满分且 spawn_x 与构造值精确一致.

第一次造这个合成观测时用错了参数: `terrainsim.terrain_profile` 的海滩默认值 340, 而种子 123456
的真实值是 364. 这 24 格差异永久改变地形特征推进计数, 使真种子只拿到 0.1081 分 (探针查到).
修正后即得 1.0000.

### 判定门槛 (主画面观测)

合成用例中真种子 1.0000, 假候选上限 0.7027. 真实观测含提取误差, 真种子预期 0.85~0.95.
故判定线设 **0.80**; 跨观测复核改用游戏内特征核对 (空岛+传奇星怒, 金字塔+发光蘑菇+龙蛋),
不再使用已作废的地图观测.

### 复核链路的两个缺陷 (与 GPU 侧同类)

| 缺陷 | 后果 | 修法 |
| --- | --- | --- |
| `verify_top.py` 挑最优对齐用 `trim` (截尾 +-1.5 松容差) | 选中错误对齐, 再打印该对齐下的逐格率, 真种子被判低分, 假候选反超 | 改用 `exact` (逐格) 挑选 |
| `shift = round(col / scale)` | 尺度约定与 C/CUDA 相反 | 改为 `round(col * scale)` |

### 精度必须全程保留

`ingame_profile.py` 与合成观测生成脚本都用 `f"{v:.0f}"` 写文件, 把 0.042 格精度四舍五入掉.
后果: 完全对齐时残差变成 +-0.5 的均匀抖动, 只有约 84% 过 0.5 容差, 真种子满分被压到 0.84,
与假候选的 0.89 混在一起. 改为保留三位小数, 并在复核端把两侧统一量化到 1/8 格后:

```
        seed    逐格     spawn    尺度
      123456  100.0%    3200   1.00     <- 真种子, 领先 23 个点
      123263   77.0%    3190   0.97
      123645   75.7%    3203   0.94
```

GPU 端 1.0000, Python 端 100.0%, 两边一致且都排第一.

### 两帧拼接 (155 格)

### 定位到它的关键两步

1. **格宽**: 早期用"地表高度必为整数"自动定标得到 21.25~22.25, 在近乎平坦的地形上这条判据会
   奖励最平滑的采样, 因此系统性偏大 10~15%, 使整份观测被横向拉伸. 用户直接量游戏内方块得到
   20.86 后, 台阶率从 0.0% 恢复到 9% 量级, 四张截图重叠区两两误差降到 0.04 格.
2. **出生点范围**: 内核的 sx 参数是出生点世界列, 代码内部自行减 marker. 一度误传了已减过的值,
   使搜索整体错位 141 列, 那几轮的全部结果都是错的 (表现为每批打满 100 条、榜首 0.93 却找不到).
